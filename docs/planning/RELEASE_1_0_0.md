# Stable 1.0.0 preparation

## Approved outcome

Prepare `@vmitsaras/raveldex`, `@vmitsaras/raveldex-english` and
`@vmitsaras/raveldex-astro` for version `1.0.0`. Simplify installation,
documentation and contributor/agent onboarding. Create native GitHub issue
trees for later demo and consumer-interface polish; do not implement that polish
as part of release preparation.

The canonical roadmap owns N12 (release preparation), N13 (optional demo work)
and N14 (optional interface/recovery work). Existing accepted tasks remain done.

## Contracts

- Preserve native TypeScript/ESM architecture, public exports/types/CSS hooks,
  exact totals/order/revisions, atomicity, source offsets, ownership and limits.
- Use version `1.0.0` and exact matching core peers in all three library
  manifests. Configure public npm access. Example applications remain private.
- Keep current Node/Astro requirements and dependency versions. Preparation
  must never publish, create releases/tags, read release credentials or deploy.
- Registry installation is the normal consumer path. Offline tarballs remain
  the reproducible maintainer/test path. Keep existing preparation commands.
- Remove development-status prose from public guides and package contents.
  Preserve actual compatibility, accessibility and performance limitations.
- Delete only superseded documents with retired references. Preserve accepted
  evidence, executable fixtures, provenance and third-party licenses. Do not
  rewrite history or remove large evidence archives to reduce checkout size.
- Keep a concise current project map and task handoff instead of chronological
  agent narratives. Do not add a parallel agent-documentation system.

## Optional issue trees

N13 covers choosing a presentation, everyday copy/counts/status, readable
excerpts and optional diagnostics, and progressive disclosure/adoption.
N14 covers inline/modal, dropdown/full-results, directory/cards and visible
optional-feature/adapter recovery journeys. Adapters remain headless.

Each child records source-backed findings separately from the design review of
the stale generated snapshot, user impact, bounded changes, measurable
acceptance criteria and focused verification. Preserve the existing Raveldex
identity. Include keyboard/focus, composition, cancellation/stale work,
loading/error/empty/retry, narrow/long/RTL content, themes, reduced motion,
no-JavaScript browsing and relevant manual accessibility checks.

Use managed roadmap issue sections and actual native sub-issue relationships.
Link only the explicitly selected overview, preserve existing parents and
milestone membership, paginate/read back results and make repeat linking a
zero-write operation. Optional tasks stay open and are not automatically selected.

## Acceptance and verification

1. Stable publishable manifests, strict package inventories, isolated installed
   imports/declarations/CSS/examples and matching companion installs pass.
2. Current guides use normal installation and usable package-local references;
   required instructions do not depend on access to the private repository.
3. Agent/contributor entry points identify architecture, relevant source/tests,
   focused commands, lifecycle constraints and current work without old history.
4. Regenerated Pages and starter archives match final source identities, public
   exclusions and links. Focused and complete site regressions pass.
5. N13/N14 native relationships read back correctly; a repeat link is idempotent.
   Existing completed tasks/issues and unrelated hierarchy/notes are preserved.

Run focused packaging/linker checks first. Build through the existing complete
candidate preparation, then reuse its compiler output for companion packaging
and site generation. Reuse unchanged historical benchmark/human AT results only
within their original identities and scope. Record unavailable checks explicitly.
Confirmed essential defects block the affected release claim.

## Review baseline and delivery

Baseline is `ad42057`: 80 accepted tasks, private `0.1.0-rc.0` library manifests,
336 Markdown documents and stale generated Pages (24 input mismatches).
The prior browser design review examined only that generated snapshot. It found
engineering-heavy wording, numerical diagnostics and raw Markdown excerpts;
those observations require confirmation against regenerated output before a
runtime defect is asserted.

Approximately 8.5 GB of tracked evidence is a separate checkout-footprint
finding. No retention migration or history rewrite is selected here.

Delivery is uncommitted repository changes, verified local artifacts and actual
issue links. Commits/pushes, registry publication, GitHub releases/tags,
repository visibility and hosted deployment are separate actions.
